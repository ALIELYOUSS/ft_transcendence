Engineering handbook · v0.1

WeMeet, from the socket up

WeMeet is our ft_transcendence project: a social platform where people pick shared interests, find each other, and set up real-life meetups (we call them slots) with a group chat attached. This handbook explains how the code is put together, why each piece is there, and how to run it.

It grows with the code. Each feature we merge adds its own section and a changelog entry.

Setup & running

Docker runs the whole stack. Node is needed on your machine only if you want hot reload outside containers.

Prerequisites

ToolVersionWhy
Docker Engine + Compose v224+Runs db, backend, frontend, nginx and adminer
Node.js22 LTSSame as the node:22-alpine images. Only needed for local dev and running the Prisma CLI
OpenSSLanyGenerates the self-signed TLS certificate for Nginx
A Google Cloud OAuth client—Needed for "Continue with Google"

  1. Clone and enter the repo

    shell
    git clone <repo-url> ft_transcendence
cd ft_transcendence

  2. Create the backend environment file

    Copy the template, then fill in every value. Never commit backend/.env: .gitignore already blocks .env and .env.*, with .env.example as the only exception.

    shell
    cp backend/.env.example backend/.env
# generate a strong secret (run twice: access + refresh)
node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
    VariableUsed byMeaning
    DATABASE_URLPrismaService, prisma.config.tsPostgres connection string. Compose overrides it to point at the db host
    ACCESS_TOKEN_SECRETAuthService, JwtGuardHMAC key for signing 15-minute access tokens
    REFRESH_TOKEN_SECRETAuthServiceA different HMAC key for 7-day refresh tokens
    GOOGLE_CLIENT_IDgoogle-oauth.config.tsOAuth client ID from Google Cloud Console
    GOOGLE_CLIENT_SECRETgoogle-oauth.config.tsOAuth client secret
    GOOGLE_CALLBACK_URLgoogle-oauth.config.tshttps://localhost/api/auth/google/callback
    FRONTEND_URLAuthControllerWhere Google sign-in redirects back to, e.g. https://localhost
    PORTmain.tsDefaults to 3001
    Startup checkIf any of the required variables (database URL, both token secrets, the three Google values) is empty, the backend stops right away with Missing environment variables: …. If you see that in docker compose logs backend, fill in backend/.env.

  3. Register the Google OAuth client

    In Google Cloud Console → APIs & Services → Credentials, create an OAuth client ID of type Web application. Add https://localhost/api/auth/google/callback as an authorized redirect URI, and put the ID and secret in backend/.env.

  4. Generate the TLS certificate

    Nginx loads nginx/certs/nginx-selfsigned.crt and .key. The certs folder has its own .gitignore, so each developer makes their own.

    shell
    openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout nginx/certs/nginx-selfsigned.key \
  -out nginx/certs/nginx-selfsigned.crt \
  -subj "/CN=localhost"

  5. Build and start the stack

    shell
    docker compose up --build -d
docker compose ps           # all five services should be "running"
docker compose logs -f backend

  6. Apply database migrations

    The backend container runs npx prisma migrate deploy before it starts, so a fresh database gets its tables automatically. It only applies pending migrations and never drops data. To apply a new migration without rebuilding, run:

    shell
    docker compose exec backend npx prisma migrate deploy

  7. Open it

    URLWhat
    https://localhostThe app. / redirects to /auth/login. Accept the self-signed certificate warning
    https://localhost/api/auth/…The backend auth API, through Nginx
    http://localhost:3001/docsSwagger UI, served directly by the backend
    http://localhost:8080Adminer. Server db, use the credentials from compose

Developing with hot reload

Run only Postgres in Docker and the apps on your machine:

shell
docker compose up -d db
cd backend  && npm install && npx prisma generate && npm run start:dev   # :3001
cd frontend && npm install && npm run dev                                   # :3000
Heads upThe frontend calls relative URLs such as /api/auth/login, and only Nginx maps them to the backend. Under next dev those calls return 404 until we add a rewrites() rule in next.config.ts. Until then, test auth through https://localhost. In local dev, DATABASE_URL must use localhost:5432 instead of db:5432.

System

Architecture

Every browser request lands on Nginx over HTTPS. Nginx sends /api/* to NestJS and everything else to Next.js. Only NestJS talks to Postgres.

Backend Dockerfile

backend/Dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci                                  1
COPY prisma ./prisma
COPY prisma.config.ts ./
ENV DATABASE_URL=postgresql://…@db:5432/…    2

COPY tsconfig*.json nest-cli.json ./

  1. npm ci installs exactly what the lockfile says. Copying package*.json before the source lets Docker reuse this layer while the dependencies are unchanged.
  2. prisma.config.ts calls env('DATABASE_URL'), so prisma generate fails without a value. The value is only a placeholder at build time; the real one comes from compose at runtime.
  3. nest build compiles TypeScript to dist/.
  4. Applies any pending migrations with prisma migrate deploy, which never drops data, then runs node dist/main. If a migration fails, the container exits and you see why in docker compose logs backend.

Frontend Dockerfile (multi-stage)

nginx/default.conf routing

Server / locationGoes toWhy
listen 80301 https://$host$request_uriForces HTTPS
location /api/http://backend:3001/Every backend module. The trailing slash on proxy_pass strips the /api prefix, so /api/auth/login reaches Nest as /auth/login
location = /302 /auth/loginThe bare domain redirects to the login page, so the browser URL matches the Next route
location /http://frontend:3000All other pages and assets, path unchanged. Passes the Upgrade/Connection headers that Next HMR and later WebSockets need
Don't put a path on the catch-allWith a path, as in proxy_pass http://frontend:3000/auth/login inside location /, nginx replaces the matched / with that path for every request. /_next/static/x.js becomes /auth/login_next/static/x.js and returns 404, so the page loads with no CSS or JS, React never hydrates, and forms never call the API. Also: after editing default.conf, run docker compose restart nginx, because editors that replace the file break the single-file bind mount and nginx -s reload keeps reading the old copy.

Every proxied location forwards Host, X-Real-IP, X-Forwarded-For and X-Forwarded-Proto, so the backend can see the real client IP and the original scheme. New backend modules need no nginx change: anything under /api/ reaches Nest.

How Prisma is wired

backend/src/prisma/prisma.service.ts
@Injectable()
export class PrismaService extends PrismaClient implements OnModuleInit {   1
  constructor() {
    const adp = new PrismaPg({ connectionString: process.env.DATABASE_URL });  2
    super({ adapter: adp });
  }
  async onModuleInit() { await this.$connect(); }                       3
}
  1. Because the service is a PrismaClient, any class that injects it can call this.prisma.user.findUnique(...) directly.
  2. Prisma 7 uses driver adapters: PrismaPg sends queries through the pg package instead of Prisma's own Rust engine.
  3. Nest lifecycle hook: connects once when the module starts, so the first request doesn't pay the connection cost.

PrismaModule provides and exports PrismaService. Any feature module that needs the database adds imports: [PrismaModule].

NestJS structure

Nest organizes code in modules. A module groups controllers (HTTP routes) and providers (injectable classes such as services and guards). Nest's dependency-injection container creates each provider once and hands it to whatever asks for it in a constructor.

Google config & strategy

backend/src/auth/google.strategy.ts
export class GoogleStrategy extends PassportStrategy(Strategy, 'google') {
  constructor(configService: ConfigService) {
    super({
      clientID:     configService.getOrThrow('google.clientId'),    1
      clientSecret: configService.getOrThrow('google.clientSecret'),
      callbackURL:  configService.getOrThrow('google.callbackURL'),
      scope: ['email', 'profile'],
    });
  }
  validate(accessToken, refreshToken, profile) {                       2
    return { googleId: profile.id, email: profile.emails?.[0]?.value,
             username: profile.displayName, avatarUrl: profile.photos?.[0]?.value, … };
  }
}
  1. google.* keys come from registerAs('google', …) in google-oauth.config.ts. getOrThrow crashes at boot if a key is missing, so a misconfigured environment fails fast.
  2. Passport calls validate after exchanging the code with Google. Whatever it returns becomes req.user in the controller. Google's access and refresh tokens are returned too but never used, so they can be dropped.
Backend

AuthService, method by method

backend/src/auth/auth.service.ts holds all the auth logic. It injects PrismaService and uses bcrypt and jsonwebtoken.

reg(dto: CreateAuthDto) called by create() ← POST /auth/register

Registers a local account.

Steps
1. Look up the email and throw ConflictException if it's taken. 2. bcrypt.hash(password, 10). 3. Create the user, attaching interests with connectOrCreate so unknown interest names are created on the fly. 4. Return the user with interests and without password.
Returns
User without the password
Issues
The username isn't checked before insert, so a duplicate username causes a Prisma error (500) instead of a 409.
login(email, password) POST /auth/login

Finds the user by email, rejects accounts without a password (Google-only users), compares the password with bcrypt, then calls createTokens.

Returns
{ response: user, accessToken, refreshToken }
Issues
Bug response still contains refreshedToken (only password is stripped). Bug bad credentials throw ConflictException (409) where UnauthorizedException (401) is correct. The error message is the same for an unknown email and a wrong password, which is right, because it doesn't reveal which emails exist.
loginWithGoogle(googleUser) GET /auth/google/callback

Find-or-create for Google identities.

Steps
1. Require an email. 2. Look up by googleId, then fall back to email. 3. If found, set googleId on the user (this links an existing local account). 4. Otherwise create a user named <displayName>-<last 6 of googleId> with password: null. 5. Issue tokens.
Returns
{ response, accessToken, refreshToken }, with password and refreshedToken stripped
Issues
Risk linking by email without checking email_verified could let someone take over an account. The Google avatarUrl is not saved.
private createTokens(userId) internal

Signs { sub: userId } twice: with ACCESS_TOKEN_SECRET for 15 minutes and with REFRESH_TOKEN_SECRET for 7 days. Stores bcrypt.hash(refreshToken) in user.refreshedToken, so a database leak doesn't expose usable tokens.

Effect
One active refresh token per user. Logging in on a second device signs the first one out at its next refresh.
refresh(refreshToken) POST /auth/refresh

Verifies the JWT signature and expiry, loads the user, compares the token against the stored hash, then calls createTokens again, which rotates the token: the old one stops working.

Returns
{ accessToken, refreshToken }
Missing
Reuse detection: replaying an old token is rejected, but it doesn't revoke the session.
logout(refreshToken) POST /auth/logout

Verifies the token, then sets refreshedToken = null, so no refresh token works for that user anymore. Access tokens stay valid until they expire (15 minutes at most).

findAll() · findOne(id)

Return only { id, email } through a Prisma select. This is the safe pattern; copy it everywhere.

update(id, dto) · remove(id)

update drops interests and writes the rest of the DTO. remove deletes the row.

Issues
Critical both return the full row, password hash and refresh hash included. update saves password as plain text if one is sent. See Known issues.
Backend

Guards & DTOs

A guard is a class with canActivate(). It returns true to let the request through, or throws to stop it. @UseGuards(A, B) runs the guards in order, so JwtGuard always comes first and sets request.user for the guards after it.

JwtGuard Guards/guards.ts

Reads Authorization: Bearer <token>, verifies it with ACCESS_TOKEN_SECRET, requires a sub claim, and sets request.user = { sub }.

Fails with
401 "Bearer access token is required" or 401 "Invalid access token"
AdminGuard

Loads role for request.user.sub and allows only ADMIN. It reads the role from the database on every request, not from the token, so a demotion takes effect immediately.

OwnerOrAdminGuard

Allows the request if request.user.sub === params.id. Otherwise it falls back to the admin check. Used on GET/PATCH/DELETE /auth/:id.

Improve
Throw ForbiddenException (403) for "logged in but not allowed"; 401 means "not logged in".

DTOs

A DTO (data transfer object) is a class whose decorators describe what a valid request body looks like. ValidationPipe checks every incoming body against it.

DTOFields & rulesStatus
CreateAuthDtousername string, not empty · email IsEmail · password string, 8–20 characters (@MinLength(8), @MaxLength(20)) · interests string[], at least 1OK

Conventions

Backend

  • One Nest module per feature: feature.module.ts, .controller.ts, .service.ts, dto/. Generate it with nest g resource <name>.
  • Controllers only parse input and call the service. Business logic and Prisma calls stay in services.
  • Every request body gets a DTO with class-validator decorators. No inline @Body() x: {…} types.
  • Never return a Prisma model directly. Always select the fields the client needs, and never password or refreshedToken.
  • Throw Nest HTTP exceptions with the right status: 400 validation, 401 not logged in, 403 not allowed, 404 not found, 409 conflict.
  • Configuration comes from ConfigService. Don't read process.env inside services.

Frontend

  • Route files in app/ stay thin. UI lives in components/<feature>/.
  • Add "use client" only to components that need state, effects or event handlers.
  • Use brand tokens; don't add new hex values.
  • File names: kebab-case (interest-picker.tsx). The older login_card.tsx files should be renamed.

Git

  • Branch per feature off main. Conventional commits: feat(auth): …, fix(db): …, docs: ….
  • A schema change ships with its migration in the same commit.
  • Every feature PR updates this handbook: the relevant section, Known issues, Roadmap status and Changelog.

2026-11-08

fix: nginx routing + auto migrations

The catch-all location / had proxy_pass http://frontend:3000/auth/login, which rewrote every asset path, so all /_next/static files returned 404 and the login page had no UI or JS. /api/ also forwarded the prefix to Nest, which caused 404s. The new config adds a / → /auth/login redirect, a passthrough catch-all, /api/ → backend:3001/ with the prefix stripped, and brings back the HTTP→HTTPS redirect. The backend container now runs prisma migrate deploy on start, which fixes the relation "public.User" does not exist 500 on a fresh database.
